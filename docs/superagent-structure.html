superagent: structure and harness architecture

How the plugin is put together: the skills, the goal vault they maintain, the loop that drives them, the ten agent roles, and how each supported harness (Claude Code, Codex, Cursor, Pi) dispatches those roles differently. This page is the structural reference; the README covers installation, quick start, and the configuration key table.

1. Overview

superagent turns a goal description into a tree of self-reviewed plans and then walks that tree to completion, one step per tick, committing every artifact through pull requests. It has two layers:

  • Plan-tree skills (supergoal, superplan, superrun, superfinish) that author and execute plans in a goal vault, a folder of markdown plans, findings, and reports.
  • An autonomy driver (the superagent supervisor, built on the superloop clause library) that fires a tick on an interval, dispatches exactly one planning or execution step per tick, and advances a state machine kept in a gitignored loop-status file.

The canonical implementation is a Claude Code plugin. Three generated builds run the same skills on Codex, Cursor, and Pi. Every build ships the same scripts/ directory, so the scheduler, the tick, and the bridge behave identically; what differs is how each harness's supervisor can start and wait on a child agent, which is the subject of section 7.

3. The goal vault and the plan tree

A goal lives in <SUPER_GOAL_ROOT>/<STAMP>-<slug>/, where the stamp is the UTC creation time (YYYY-MM-DD-hh_mm) and the root defaults to vault. supergoal creates six dated subfolders and a routing map:

PathHolds
goal-directives.mdThe authoritative routing map: what belongs in each folder, the file-naming convention, wikilink convention, and a "which folder?" decision flow.
master-plans/The root master plan and every sub-master plan. Each carries a progress-report table.
plans/Leaf implementation plans, one PR each. A leaf has no progress-report table; that absence is the leaf marker.
findings/Investigation notes written before or during implementation.
reports/Closeout reports written by superfinish.
handoff/Session-continuity documents.
todo/Deferred backlog.
loop-status/The gitignored loop-status file (section 4). Sibling of master-plans/, never committed.

The plan tree. Every master or sub-master plan opens with a progress-report table whose columns are Step | Status | Plan | PR | Comments. The Plan column links down to the step's child plan. Every non-root plan carries a parent-seed reference near the top, the "up" link. The root is exactly the plan with no parent reference. Together these form seed/master → sub-master → implementation-plan leaves.

How supertraverse walks it.

  • Planning-mode descent (superplan): pre-order depth-first search down Plan links, skipping closed rows and recursing into internal nodes. The target is the first not-done row with no child link. It returns the target plus the path from the root, which planning-mode ascent then uses to mark ancestors "in progress (planning underway)" without ever downgrading a row.
  • Execution-mode descent (superrun): the same search, but the target is the first not-done row whose child is a leaf that is itself incomplete, judged from the leaf's own closeout banner so the walk is idempotent.
  • Completion-mode ascent (superfinish): walks parent references upward, flipping the leaf's row to executed or merged, and each ancestor to complete only when all of its children are merged on main.
  • Both descents can return none (nothing to do) or not-traversable (the root lacks a progress table). The supervisor treats the latter as an escalation trigger.

4. The loop: status file, states, drivers

The loop-status file

All loop state lives in one gitignored file per goal at <primary root>/<SUPER_GOAL_ROOT>/<goal>/<SUPER_LOOP_STATUS_DIRNAME>/<date>-<slug>.md. It is always resolved against the primary checkout, never a worktree, so it survives every skill's branch switching. YAML frontmatter holds the machine state (master_plan, status, plan_exhausted, prior_status, driver, cron_id, created, iteration, session_skill_count, and a ci_wait block while parked on CI). The body is append-only: ## Pending decision, ## Decisions, ## Iteration log.

StatusRoleWhat a tick does
WAITING FOR PLANreadySync gate, set PLANNING, dispatch superplan, sync gate and be-sure, parse the Final Report, transition, log.
PLANNINGtransientOnly ever seen inside a tick. Persisted = crash; reset to WAITING FOR PLAN.
WAITING FOR RUNreadyAs above with superrun and RUNNING.
RUNNINGtransientPersisted = crash; reset to WAITING FOR RUN.
WAITING FOR CIparkedA superrun pushed a long CI run and yielded a CI-PENDING report. Cron driver: an event-fired Monitor owns the wait and the tick is a strict no-op. External driver: the tick script checks the recorded run ids with gh run view in bash and exits without a session until every run is terminal.
WAITING FOR INPUTparkedA decision the escalation ladder could not resolve. The tick applies a recorded answer: if present; otherwise the tick script exits before launching a session.
DONEterminalNo-op, then the driver disarms itself (SUPER_AUTO_DISARM_ON_DONE).

Answering a parked decision. An unattended tick that reaches L7 rung 2 writes a ## Pending decision block with the question, the panel's per-option analysis, and the instruction to write answer: <option> under it, saves the current status into prior_status, sets WAITING FOR INPUT, releases the lock, and exits. The driver notifies once. scripts/answer.sh <slug> "<option>" records the answer under the lock and kicks a tick, which appends it to ## Decisions, restores prior_status, and continues.

5. Anatomy of an external tick

scripts/superagent-tick.sh is stateless: it reads and writes the loop-status file and nothing else, and never resumes a session. In order:

  1. Resolve inputs. REPO from the environment or git rev-parse; LOOP_FILE from the environment or the first argument; the log file, /tmp/superagent-<loop-basename>.log by default; an optional TICK_TIMEOUT wrapped in timeout or gtimeout.
  2. Load configuration. Source the repo's .env for API keys, then load_superenv (section 10).
  3. Input gate. If the status is WAITING FOR INPUT with no answer: line, log one line and exit 0. No session.
  4. Harness preflight. Resolve SUPER_HARNESS, check the CLI binary is on PATH (after prepending SUPERAGENT_CLI_PATH, recorded at install time so nvm-installed CLIs resolve under launchd), check gh auth.
  5. CI gate. If the status is WAITING FOR CI, query every run id in ci_wait.runs. Exit 0 without a session while any is still running, unless the park is older than SUPER_CI_MAX_WAIT_MIN (default 180), in which case notify ci-stale once and let the session run. Fails open on any query error.
  6. Pick the skills root and model. Claude: the repository root; Codex, Cursor, Pi: the generated build directory (exit 7 if missing). The supervisor model comes from TICK_MODEL or SUPER_MODEL_SUPERVISOR. A harness prefix equal to the tick's harness is stripped; any other prefix is refused with exit 11. On Claude, inherit becomes the literal claude-opus-4-8 because a headless session has no model to inherit; on the other harnesses it omits the flag so the CLI's own default applies.
  7. Export bridge paths and timeouts. SUPERAGENT_BRIDGE and SUPERAGENT_FANOUT always; SUPERAGENT_PI_SKILLS on Pi; BASH_DEFAULT_TIMEOUT_MS (1 h) and BASH_MAX_TIMEOUT_MS (2 h) so a Bash tool waiting on superrun or a foreign CLI is not killed at the 10-minute default.
  8. Resolve effort. TICK_EFFORT or SUPER_EFFORT_SUPERVISOR; dropped with a warning on Cursor; on Claude, warn if CLAUDE_CODE_EFFORT_LEVEL is set because it outranks every pin.
  9. Take the lock. Export SUPERAGENT_TICK_PID and trap EXIT to reap only a lock this PID owns.
  10. Launch one headless CLI with a prompt that says: read skills/superagent/SKILL.md, run exactly one --tick on this loop file, never ask a question, park instead. The prompt is a file read rather than a skill invocation because a headless session cannot run slash commands.
  11. Post-checks. Claude only: a log segment saying background tasks were still running after the print-mode ceiling becomes exit 9. Any harness: exit 0 with a persisted transient status and no live lock owner becomes exit 10.
  12. Notify and disarm. Fire waiting-for-input or done notifications on the transition; on DONE, call uninstall-timer.sh <slug> --from-tick.

The scheduler layer

Every lifecycle script discovers loops through the per-goal registry file ${XDG_CONFIG_HOME:-$HOME/.config}/superagent/<slug>.env, where the slug is the goal folder's basename with its timestamp stripped. The file records the repo, the script directory, the loop file, the harness, the CLI path, and any tick overrides. The interval is not in it; it lives in the timer drop-in or the plist.

ScriptDoes
launch.shDerives the slug, creates or reuses the loop file (a direct write, no LLM), fails fast on missing CLI or gh auth, calls install-timer.sh, then kicks the first tick immediately.
install-timer.shWrites the registry file, then arms a launchd LaunchAgent (macOS: rendered plist, launchctl bootstrap) or a systemd user timer (Linux: templated unit plus an interval drop-in, loginctl enable-linger).
uninstall-timer.shDisarms the entry. Waits out an in-flight launchd tick unless --from-tick (the DONE self-disarm path). --purge also removes the registry file.
stop.shGraceful drain by default; --hard also SIGTERMs the in-flight tick. The loop file is always preserved.
force-stop.shFor a wedged tick: halt it, remove the stale .lockd directory unconditionally, then kick a recovery tick whose crash-recovery resets the transient status. Dry-run unless --apply.
status.shTable or JSON across every registered loop; drill-in shows the pending decision, recent log lines, and the tail of the tick log.
answer.shWrites answer: under the pending block while holding the lock, then kicks a tick.
bootstrap.shAttended alternative to launch: runs the supervisor's fresh-start form once through a live headless CLI, prints the loop file path.
console-watch.shRead-only poller that prints a wake sentinel and notifies on WAITING FOR INPUT or DONE.

6. The ten roles and the SDD loop

Each role has a SUPER_MODEL_<ROLE> key and a SUPER_EFFORT_<ROLE> key. Three roles are dispatched by the supervisor; six are dispatched by the executor while it runs an implementation plan.

RoleDispatched byRuns
SUPERVISORthe scheduler or the sessionThe tick itself. Native-only; a foreign prefix is exit 11.
PLANNERsupervisorsuperplan or supergoal.
EXECUTORsupervisorsuperrun, the SDD controller. Always its own CLI process.
PANELsupervisorThe three read-only L7 panelists.
IMPLEMENTERexecutorOne fresh agent per plan task; resumed for fix rounds 1–3.
TASK_REVIEWERexecutorSpec-compliance and code-quality review after each task. Reports every finding with severity and confidence; the executor filters (SUPER_REVIEW_CONFIDENCE_FILTER).
RE_REVIEWERexecutorScoped re-review after each fix round.
FIX_PLANNERexecutorFix rounds 4–5: diagnoses the root cause and writes the exact edit.
FIX_APPLIERexecutorApplies the fix-planner's edit.
BRANCH_REVIEWERexecutorWhole-branch review once per plan, before the code PR.

Why the executor is a process, not a subagent. superrun must foreground-wait on its own implementer and reviewer children. A subagent cannot foreground-wait on children it spawns: they background and yield. Before 0.5.1 superrun ran as an Agent-tool subagent and decayed into a nudge spiral with two writers racing on the worktree (issue #25). Now the supervisor starts it through role-bridge.sh --tools executor from its Bash tool as a fresh top-level CLI process. Inside that process the SDD children are depth 1 and the synchronous wait holds. The same depth-1 rule is why the supervisor that runs the panel must itself be the top-level agent.

How a model or effort pin reaches a role

  • inherit: omit the parameter; the session or tick model applies.
  • A Claude tier name (sonnet, opus, haiku, fable): passed directly as the Agent or Task tool's model: parameter.
  • A full Claude ID (claude-…) or any non-inherit effort on Claude Code or Cursor: the tool's model: parameter is tier-only and there is no effort parameter, so the pin rides the frontmatter of a generated agent definition, .claude/agents/super-<role>.md (or .cursor/agents/), and the role is dispatched with subagent_type: super-<role>. A missing definition is a hard error that says to re-run init.
  • On Codex, there are no definition files at all. Every pin rides the spawn_agent call's model and reasoning_effort parameters.
  • On Pi, the six SDD roles get .pi/agents/super-<role>.md definitions; planner, executor, and panel take their pins as CLI flags on the bridge call.
  • A bridged role (its harness differs from SUPER_HARNESS): see section 8.

8. The bridge: role-bridge.sh, bridge-fanout.sh, relays

scripts/role-bridge.sh runs one agent role on a harness CLI headless, on a prompt read from a file, and prints only the CLI's final message to stdout. It is used for three different things: the executor on every harness, every heavy dispatch on Pi, and the far end of a relay for a bridged role.

Evidence lines. Before the CLI starts, the bridge writes a header to $TMPDIR/superagent-bridge/<role>-<stamp>.log and echoes the path on stderr as role-bridge: log=<path>:

role-bridge: start=<utc> harness=… model=… effort=… tools=… role=… cwd=…
role-bridge: end=<utc> exit=<0|3|4> secs=<n> result_bytes=<n>

A header with no trailer means the bridge was killed mid-run. mix-e2e.sh parses these lines to prove that every pinned role ran on its pinned harness and model. Exit codes: 0 ok, 2 CLI not on PATH, 3 CLI exited non-zero, 4 CLI exited 0 with an empty result, 64 usage.

bridge-fanout.sh runs N role-bridge.sh children concurrently, one per --prompt-file, with a shared watchdog (--timeout, default 1800 s), and blocks until all finish. Output is framed per child as === PANELIST <n> exit=<rc> === … === END <n> ===, with BRIDGE-FAILED exit=… harness=… role=… log=… in place of a failed child's output. It is the L7 panel primitive for a supervisor that has no blocking parallel subagent tool, which today means Pi.

Relays

A relay is a native subagent whose only job is to write the prompt it received to a file, call role-bridge.sh for the foreign harness, and return the bridge's stdout verbatim. It is told in strong terms never to answer the prompt itself, because a capable model given a short task will otherwise just do it: this is why SUPER_BRIDGE_RELAY_MODEL must not be weakened to haiku, which was measured to answer instead of relaying, and why every build pins it rather than letting it float with the CLI's default subagent model.

  • templates/super-role-bridge-agent.md: the Claude Code and Cursor relay definition. Frontmatter carries model: <relay-model> and tools: Bash; init renders it to .claude/agents/super-<role>.md for each bridged role.
  • templates/super-role-pi-bridge-agent.md: the Pi relay definition for a bridged SDD role, rendered to .pi/agents/super-<role>.md.
  • templates/relay-preamble.md: the Codex form. No file is generated; the loop renders the preamble inline as the spawn message with the relay model as the spawn's model.

A reply that begins BRIDGE-FAILED is treated as a crashed child: retry once, then the skill's normal escalation, quoting the log= path. For a panelist it counts as insufficient-info, never a crash of the rung.

The executor never goes through a relay on any harness, and the supervisor can never be bridged. On Pi the planner and panel do not go through one either. So SUPER_BRIDGE_RELAY_MODEL matters for the planner, panel, and SDD roles on Claude Code, Codex, and Cursor, and for the SDD roles only on Pi.

The L7 ladder

Triggers: a CRITICAL finding, a not-traversable result, a BLOCKED or CI-red Final Report, or any place a delegated skill would otherwise ask the user. Every trigger is surfaced in the tick's "Findings & issues" line even when rung 1 resolves it.

Rung 1, the panel. Three independent panelists receive an identical packet: the decision or blocker, the plan and report excerpts, and pointers into the code and vault. Each returns a chosen option, a rationale, and a confidence, or insufficient-info. Two of three in agreement with non-low confidence is adopted and recorded under ## Decisions. The supervisor's option set is: retry superrun with the decision as guidance, re-plan (route to WAITING FOR PLAN), or mark the step declined.

Rung 2, the user. Reached only when the panel splits or all abstain. An attended session asks immediately and continues the same tick. An unattended tick writes the pending block, sets WAITING FOR INPUT, releases the lock, and exits; resume is automatic on the first tick that finds an answer:.

10. Configuration resolution

Model grammar. A model key is inherit or [<harness>:]<model>. The prefix is inferred when omitted: a Claude tier name or claude-* means claude; gpt-*, o<digit>*, or codex* means codex; anything containing / means pi; cursor is never inferred. A role is native when its resolved harness equals SUPER_HARNESS and bridged otherwise. Unrecognised values warn and fall back to inherit, except the supervisor, where a foreign harness is a hard error in both init and the tick.

Effort domains. Validated in the role's own resolved harness, not the supervisor's: claude low | medium | high | xhigh | max; codex none | minimal | low | medium | high | xhigh; pi off | minimal | low | medium | high | xhigh | max; cursor inherit only.

The full key table with shipped defaults and the reasoning behind each is in the README's Key reference. The keys fall into six groups: models and effort per role, harness (SUPER_HARNESS, SUPER_CODEX_SANDBOX, SUPER_PI_SUBAGENTS), paths, loop tuning (interval, lock steal window, heavy-step limit, the input and CI gates, notification command), CI and test-evidence policy, and git and PR policy.
